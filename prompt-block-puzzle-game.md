# Промпт для Claude Code: Android-игра "Block Puzzle 8x8"

Скопируй этот текст целиком в Claude Code как стартовое задание.

---

## Что нужно сделать

Разработать нативное Android-приложение — головоломку типа "block puzzle" (аналог Block Blast / Woodoku), но с уникальной механикой: **фигуры можно свободно вращать**. Игра полностью офлайн, все данные хранятся локально на устройстве.

## Технологический стек

- **Kotlin** + **Jetpack Compose** для UI
- Архитектура: **MVVM**, состояние игры через `StateFlow` / `MutableState`
- Локальное хранилище: **Jetpack DataStore** (Preferences) для рекордов и настроек
- Минимальный SDK: **API 26 (Android 8.0)**, целевой — последний стабильный
- Никаких сетевых зависимостей, разрешений на интернет не запрашивать
- Проект должен собираться через Gradle и запускаться в эмуляторе/на устройстве без дополнительной настройки

## Игровое поле

- Сетка **8×8** клеток, квадратная, с чёткими границами между блоками
- Три ячейки "лотка" снизу/сбоку экрана — там всегда показаны **3 фигуры** для установки
- Как только игрок ставит фигуру из лотка на поле, **на её место сразу генерируется новая** (не ждём, пока все 3 будут использованы)

## Набор фигур (от 1 до 5 клеток)

Реализуй базовый набор форм, из которого генератор выбирает фигуры (все формы — базовые ориентации, повороты создаются игроком):

- **1 клетка**: одиночный квадрат
- **2 клетки**: домино (горизонтальное/вертикальное — это по сути одна форма + поворот)
- **3 клетки**: прямая тримино (I), угловая тримино (L из 3 клеток)
- **4 клетки**: квадрат 2×2 (O), прямая (I), угловая (L), угловая зеркальная (J), Т-образная (T), S и Z (зигзаги)
- **5 клеток**: крест/плюс, L-пентамино, P-пентамино, прямая I из 5 клеток, T-пентамино (можно расширить набор по своему усмотрению — главное, чтобы плотность поля росла разнообразно)

Важно: так как вращение свободное (игрок сам поворачивает), а не автоматическое перебирание всех ориентаций при генерации — **зеркальные пары (L/J, S/Z) должны быть отдельными базовыми фигурами**, потому что поворот на 90/180/270° не превращает L в J (это отражение, а не поворот).

## Механика вращения

- У каждой фигуры в лотке — кнопка/жест поворота на **90° по часовой стрелке**, без ограничения количества нажатий
- Поворот фигуры не тратит ход и не влияет на её "стоимость" при подсчёте очков
- После поворота фигура должна корректно отображаться в ячейке лотка и при перетаскивании на поле

## Установка фигур

- Drag-and-drop: перетаскивание фигуры из лотка на поле
- Во время перетаскивания — подсветка клеток, куда фигура попадёт, **зелёным**, если размещение допустимо, и **красным**, если нет
- Дополнительно: если размещение приведёт к очистке ряда/столбца, подсвечивать это заранее (превью очистки)
- Если фигуру отпустить в недопустимом месте — она возвращается в лоток

## Очистка линий

- Полностью заполненный **ряд** или **столбец** (или оба одновременно) очищается сразу после установки фигуры
- Поддержка одновременной очистки нескольких линий за один ход (комбо)
- Анимация очистки (например, вспышка/исчезновение клеток)

## Подсчёт очков

- Очки за каждую установленную клетку фигуры
- Бонус за каждую очищенную линию, с нарастающим бонусом за одновременную очистку нескольких линий (комбо-множитель)
- Точные формулы оставляю на твоё усмотрение, но вынеси коэффициенты в отдельный конфиг-объект, чтобы их легко было потом менять

## Окончание игры

- Игра заканчивается, если **ни одну из 3 фигур в лотке невозможно разместить** ни в одном месте поля
- Экран Game Over: финальный счёт, сравнение с текущим рекордом (в этом режиме), кнопки "Заново" и "В меню"

## Функция отмены хода (Undo)

- Неограниченная отмена последнего хода (и предыдущих, пока не начало игры)
- Undo должен возвращать: состояние поля, состояние лотка (какие фигуры были доступны) и счёт до хода
- Храни стек состояний в памяти на время сессии (не обязательно персистентно между запусками приложения)

## Режимы игры

### Простой режим
Фигуры выбираются случайно (равномерно или с небольшими весами) из общего набора форм, без учёта состояния поля.

### Сложный режим
Алгоритм должен **намеренно подбирать фигуры так, чтобы приблизить проигрыш**. Предлагаемый подход:
1. Для каждого хода сгенерировать несколько кандидатов на тройки фигур
2. Для каждого кандидата симулировать, сколько клеток поля останется "неудобными" (одиночные дыры, углы, которые сложно закрыть) и сколько всего валидных размещений доступно на поле после этого набора
3. Выбрать тройку, которая **минимизирует количество валидных ходов**, но не создаёт полностью безвыходную ситуацию мгновенно (чтобы игра не обрывалась через 2 хода — оставляй минимальный запас "играбельности", если это будет ощущаться нечестно, можно скорректировать)
4. Это должно быть реализовано как отдельный тестируемый модуль (например `HardModePieceSelector`), не завязанный на UI, чтобы можно было писать юнит-тесты на его логику

## Хранение данных

- Через DataStore хранить **два отдельных рекорда**: лучший счёт для простого режима и лучший счёт для сложного режима
- Рекорд обновляется автоматически при завершении игры, если текущий счёт выше сохранённого
- Никакой другой статистики (историй игр, средних значений и т.д.) не требуется — только текущий лучший результат по каждому режиму

## Экраны приложения

1. **Главное меню**: выбор режима (Простой / Сложный), отображение текущих рекордов по обоим режимам, кнопка "Играть"
2. **Экран игры**: поле 8×8, лоток с 3 фигурами, текущий счёт, кнопка Undo, кнопка паузы/меню
3. **Экран Game Over**: финальный счёт, рекорд, кнопки "Играть снова" / "В меню"

## Визуальный стиль

- Material 3, минималистичный, чистый UI
- Каждая фигура при генерации получает свой цвет из заданной палитры (чтобы визуально легче было отличать фигуры в лотке)
- Плавные анимации: постановка фигуры, очистка линий, поворот
